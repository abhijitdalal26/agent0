# Deploying agent0 to a small VM

Target: one Hetzner or DigitalOcean VM, Ubuntu 24.04, 2 vCPU / 4 GB RAM. The stack is Postgres (pgvector), a Temporal dev server, the API (`agent0 serve`), the worker (`agent0 worker`) and Caddy for HTTPS. Code runs in E2B sandboxes, never on the VM. The dashboard runs on Vercel.

```
Telegram <--(long polling, outbound only)--> api
Vercel dashboard --> https://api.example.com (Caddy :443) --> api:8000
api + worker --> temporal:7233, postgres:5432   (compose network only)
worker --> E2B (E2B_API_KEY)
```

Only Caddy publishes ports (80, 443). Postgres, Temporal and the API are not reachable from the internet.

## 1. Prerequisites

- A domain you control, with an A record pointing to the VM, e.g. `api.example.com`.
- Keys: E2B (`E2B_API_KEY`), at least one of Groq/Gemini, a Telegram bot token from @BotFather.

## 2. VM and Docker

```bash
ssh root@<vm-ip>
apt update && apt upgrade -y
curl -fsSL https://get.docker.com | sh          # Docker Engine + the compose plugin
docker compose version
ufw allow OpenSSH && ufw allow 80/tcp && ufw allow 443/tcp && ufw allow 443/udp && ufw enable
```

On a 4 GB VM add swap: `fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile`.

## 3. DNS

Create an `A` record `api.example.com -> <vm-ip>` (plus `AAAA` for IPv6). Caddy requests a Let's Encrypt certificate once the domain resolves to the VM and ports 80/443 are open. Check with `dig +short api.example.com`.

## 4. Clone and configure

```bash
git clone <your-repo-url> /opt/agent0 && cd /opt/agent0
cp infra/cloud.env.example .env.cloud
chmod 600 .env.cloud
```

Generate the secrets and paste them into `.env.cloud`:

```bash
openssl rand -hex 32   # AGENT0_API_KEY
openssl rand -hex 24   # POSTGRES_PASSWORD (hex only; it is placed in a URL)
```

`AGENT0_SECRET_KEY` is a Fernet key generated by the app, so make it after the image is built (step 5). Back it up: without it, provider keys saved from the dashboard cannot be decrypted.

Every variable in `.env.cloud`:

| Variable | Required | Purpose |
|---|---|---|
| `API_DOMAIN` | yes | Domain Caddy serves and gets a certificate for |
| `POSTGRES_PASSWORD` | yes | Password of the `agent0` Postgres user; compose builds `AGENT0_DATABASE_URL` from it |
| `TEMPORAL_IMAGE` | no | Defaults to `temporalio/temporal:latest`; pin it once things work |
| `AGENT0_API_KEY` | yes | Bearer token for the API. With `AGENT0_ENV=cloud` (set by compose) the API refuses to start while it is the default `dev-key` |
| `AGENT0_SECRET_KEY` | yes in practice | Encrypts provider keys stored via the dashboard |
| `AGENT0_CORS_ORIGINS` | no | JSON list of allowed browser origins (default `["http://localhost:3000"]`). The dashboard reaches the API through its own server-side proxy, so this only matters for direct browser calls |
| `AGENT0_TELEGRAM_BOT_TOKEN` | for Telegram | From @BotFather. Without it the bot is disabled and a warning is logged |
| `AGENT0_TELEGRAM_ALLOWED_USERS` | for Telegram | JSON list of numeric user ids or usernames. The bot refuses everyone else |
| `GROQ_API_KEY`, `GEMINI_API_KEY` | at least one | Model providers (names come from `config/models.yaml`) |
| `E2B_API_KEY` | yes | E2B sandboxes |
| `E2B_TEMPLATE` | no | Custom E2B template id; default is E2B's base template |
| `E2B_SANDBOX_TIMEOUT` | no | Max sandbox lifetime in seconds (default 1800) |
| `AGENT0_TASK_QUEUE`, `AGENT0_TEMPORAL_NAMESPACE` | no | Defaults `agent0`, `default` |

Compose sets these itself; do not put them in the file: `AGENT0_ENV=cloud`, `AGENT0_DATABASE_URL`, `AGENT0_ORCHESTRATOR=temporal`, `AGENT0_TEMPORAL_ADDRESS=temporal:7233`, `AGENT0_SANDBOX=e2b`, `AGENT0_WORKSPACE_ROOT=/data/workspaces`, `AGENT0_API_HOST=0.0.0.0`.

## 5. Start

Run compose from the repo root. An alias keeps the commands short:

```bash
alias dc='docker compose --env-file .env.cloud -f infra/docker-compose.cloud.yml'
dc build
dc run --rm --no-deps api secrets-keygen      # paste the output into AGENT0_SECRET_KEY in .env.cloud
dc up -d
dc ps
dc logs -f api worker
```

`dc` needs `POSTGRES_PASSWORD` and `API_DOMAIN` set before the first call (compose refuses to run without them). Order of start: Postgres (healthcheck), Temporal, API and worker, Caddy.

## 6. Initialise the database

The API and worker apply the schema on start, so this is normally done already. Running it by hand is idempotent and is the step to repeat after every update:

```bash
dc exec api agent0 db-init
```

Verify:

```bash
curl -i https://api.example.com/api/v1/runs                                      # 401 without the key
curl -H "Authorization: Bearer <AGENT0_API_KEY>" https://api.example.com/api/v1/runs
```

## 7. Telegram

1. In Telegram, message @BotFather: `/newbot`. Put the token in `AGENT0_TELEGRAM_BOT_TOKEN`.
2. Get your numeric id from @userinfobot and set `AGENT0_TELEGRAM_ALLOWED_USERS=["<id>"]`.
3. `dc up -d` to recreate `api` and `worker` with the new environment.
4. Message the bot: `/task <what to do>`, `/status`, `/stop <run id>`. Approvals arrive as buttons.

The bot uses long polling from the API container: no webhook and no inbound port. Run a single `api` replica, because two pollers on one token conflict.

## 8. Dashboard on Vercel

1. Import the repo in Vercel and set the Root Directory to `dashboard`.
2. Set these environment variables:
   - `HARNESS_API_URL=https://api.example.com/api/v1` (include `/api/v1`)
   - `HARNESS_API_KEY=<the AGENT0_API_KEY value>`

   These are the names the dashboard code reads today (`dashboard/src/app/api/proxy/[...path]/route.ts`). `AGENT0_API_URL` and `AGENT0_API_KEY` are not read by the dashboard. The proxy attaches the key server-side, so it never reaches the browser.
3. There is no `DASHBOARD_PASSWORD` in the code and the dashboard has no login. Anyone who can open the Vercel URL can use the API through the proxy. Until a password gate exists, enable Vercel Authentication or Password Protection (Settings, Deployment Protection) for the project, production included.
4. Deploy. If pages show mock data, check `NEXT_PUBLIC_MOCK` and `NEXT_PUBLIC_API_URL`, which `dashboard/src/lib/api.ts` still uses to decide on mocks.

## 9. Backups

Postgres holds everything durable: tasks, runs, events, memory and the encrypted secrets.

```bash
mkdir -p /opt/backups
dc exec -T postgres pg_dump -U agent0 -d agent0 -Fc > /opt/backups/agent0-$(date +%F).dump
```

Nightly via `crontab -e`:

```
0 3 * * * cd /opt/agent0 && docker compose --env-file .env.cloud -f infra/docker-compose.cloud.yml exec -T postgres pg_dump -U agent0 -d agent0 -Fc > /opt/backups/agent0-$(date +\%F).dump && find /opt/backups -mtime +14 -delete
```

Copy dumps off the VM (provider snapshots or `rclone`), and keep a copy of `.env.cloud`, especially `AGENT0_SECRET_KEY`.

Restore:

```bash
dc stop api worker
dc exec -T postgres dropdb -U agent0 agent0 && dc exec -T postgres createdb -U agent0 agent0
dc exec -T postgres pg_restore -U agent0 -d agent0 --no-owner < /opt/backups/agent0-YYYY-MM-DD.dump
dc up -d
```

The `temporal-data` volume holds in-flight workflow histories; run results live in Postgres. Artifacts live in the `workspaces` volume; archive it if you need them: `docker run --rm -v <project>_workspaces:/d -v /opt/backups:/b alpine tar czf /b/workspaces.tgz -C /d .`

## 10. Update and roll back

Take a dump first (section 9), then:

```bash
cd /opt/agent0
git rev-parse HEAD                        # note the current commit
docker tag agent0:latest agent0:previous
git pull
dc build
dc up -d
dc exec api agent0 db-init
```

Runs in flight survive the restart: Temporal resumes them on the new worker from the last finished step.

Roll back:

```bash
git checkout <previous-commit>
dc up -d --build                          # or: docker tag agent0:previous agent0:latest && dc up -d --no-build
```

The schema is applied with `IF NOT EXISTS` statements, so an older version normally runs against a newer schema. If an update changed data destructively, restore the dump taken before it.

## How the cloud sandbox works

- `AGENT0_SANDBOX=e2b` selects `E2BSandboxProvider` (`src/agent0/sandbox/e2b.py`). Commands run in an E2B microVM with `/workspace` as the working directory. No Docker socket is mounted into any container.
- The engine creates a fresh sandbox for every attempt and every verification. On create, files already in `<workspace_root>/<run_id>` are uploaded into `/workspace`. On destroy, everything under `/workspace` (except `.git`, `node_modules`, `__pycache__`, `.venv`, `.cache`) is downloaded back into that host directory, then the VM is killed. The API serves artifact downloads from that directory, which is the `workspaces` volume shared by `api` and `worker`.
- A sandbox is killed by E2B after `E2B_SANDBOX_TIMEOUT` seconds even if a command is still running.

## Why the Temporal dev server

Compose runs `temporalio/temporal` with `server start-dev --db-filename /data/temporal.db`: one container, state on a volume, no schema bootstrap, and the same server the README uses locally. `temporalio/auto-setup` is deprecated upstream and needs Postgres schema setup plus separate UI and admin containers. The cost is a single node on SQLite, fine for one agent on one VM but not for high throughput. To move later, point `AGENT0_TEMPORAL_ADDRESS` elsewhere. `agent0.orchestrator.temporal.connect` has no TLS or API-key options, so Temporal Cloud would need a small code change.

## Railway alternative (short, untested)

1. New project. Deploy this repo's root `Dockerfile` as two services: `api` (start command `agent0 serve`, with a public domain) and `worker` (`agent0 worker`).
2. Add Postgres from a pgvector template (stock Railway Postgres lacks the `vector` extension the schema needs), and a service from image `temporalio/temporal` with start command `server start-dev --ip 0.0.0.0 --headless --db-filename /data/temporal.db` and a volume at `/data`.
3. Set the variables from `.env.cloud` on both services, plus `AGENT0_ENV=cloud`, `AGENT0_ORCHESTRATOR=temporal`, `AGENT0_SANDBOX=e2b`, `AGENT0_API_HOST=0.0.0.0`, `AGENT0_API_PORT` equal to Railway's `PORT`, `AGENT0_DATABASE_URL` from the Postgres service, and `AGENT0_TEMPORAL_ADDRESS=<temporal-service>.railway.internal:7233`.
4. Caveat: Railway volumes cannot be shared between services, so artifacts mirrored by the worker are not visible to the API and artifact downloads return 404. The VM setup avoids this.
